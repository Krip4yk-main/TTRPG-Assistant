# План 25 — стан усіх внутрішніх і сторонніх сервісів у health

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** запит до нашого API або підписка через WebSocket дає структурований стан усіх внутрішніх і сторонніх сервісів (наявних і запланованих), придатний для автоматизації: моніторинг, сторонні сервіси, боти.

**Spec:** запит власника в чаті 2026-11-28: «Всі сторонні сервіси, що ми використовуємо або будемо використовувати, додай в чекер health. Статуси: працює, не підключено, лежить, зависло (англійською) і ще які потрібно. По запиту на наш API у відповіді має бути структуровано відображені всі сторонні та внутрішні сервіси і їх статуси, щоб це можна було імплементувати в сторонні сервіси чи боти й автоматизувати.»

## Стан зараз

- `GET /api/health/live` — процес живий (docker healthcheck), без звернень до сервісів.
- `GET /api/health` — `{ ok, db, redis, worker }`, статуси `ok | down | stale`, 200/503, кеш 2 с, single-flight (`backend/src/http/health.ts`).

## Global Constraints

- **Статуси (англійською, однакові для всіх сервісів):**
  - `ok` — працює;
  - `not_configured` — не підключено (немає ключів/налаштувань; це не збій);
  - `down` — лежить (помилка, відмова, таймаут з'єднання);
  - `stale` — зависло (процес є, але не просувається / дані застарілі: воркер задач, бекап давно не робився, архів логів не вивантажувався);
  - `degraded` — працює з проблемами (повільна відповідь понад поріг, частина функцій недоступна, обмеження частоти з боку сервісу);
  - `unknown` — стан ще не перевірявся (одразу після старту) або перевірку неможливо виконати.
- **Сервіси** (кожен — окремий запис; до наявних додаються майбутні, щойно їх підключено):
  - внутрішні: `mysql`, `redis`, `worker` (цикл задач), `bot` (Telegram-бот: останній сигнал життя через внутрішній API), `backup` (час останнього успішного бекапу; `stale`, якщо понад 26 год), `frontend` (статика відповідає — лише якщо адресу задано в env);
  - сторонні — **усі**, якими користуємось або плануємо (доповнення власника 2026-11-28: щось може лежати на їхньому боці, а не на нашому). Кожен — окремий запис з нашою власною перевіркою; там, де провайдер має публічну сторінку статусу, — ще й його власний статус (див. нижче):
    - `telegram_bot_api` — Bot API (`getMe` тим самим токеном, яким шле бот);
    - `telegram_login_widget` — віджет входу (скрипт `telegram.org/js/telegram-widget.js` віддається);
    - `google_oauth` — OIDC discovery `accounts.google.com/.well-known/openid-configuration` і доступність ендпоінта токенів;
    - `discord_api` — OAuth і API `discord.com/api/v10` (без витрати лімітів: легкий запит без авторизації або `gateway`);
    - `avatar_cdns` — CDN аватарів, які ми показуємо: `cdn.discordapp.com`, `lh3.googleusercontent.com`, `t.me` (userpic) — доступність (HEAD) без конкретних користувачів;
    - `backup_storage` — Cloudflare R2 / Backblaze B2 (через rclone/S3: доступ до бакета й час останнього вивантаження);
    - `logs_axiom` і `logs_archive` — План 23;
    - `tls_certificate` — сертифікат нашого домену (`PUBLIC_BASE_URL`): днів до завершення; `degraded` < 14 днів, `down` — прострочений чи недійсний (видає Let's Encrypt через Caddy — див. `docs/ops/Caddyfile.example`);
    - `dns_public` — наш домен резолвиться й відповідає ззовні по HTTPS (`/api/health/live`);
    - `cloudflare` — якщо домен за Cloudflare (план);
    - `internet_outbound` — вихідний HTTPS (потрібен для перевірки картинок та імпорту календарів з посилань користувачів).
  - **`not_configured` — для кожного сервісу явно визначено, коли він «не підключений»** (і тест на це): Telegram — немає `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME`; Google — немає `GOOGLE_CLIENT_ID`/`SECRET`; Discord — немає `DISCORD_CLIENT_ID`/`SECRET`; CDN аватарів — відповідний провайдер входу не підключено; сховище бекапів — немає `BACKUP_*`/rclone-налаштувань; Axiom/архів — немає ключів Плану 23; сертифікат і DNS — `PUBLIC_BASE_URL` не https (локально); Cloudflare — домен не за Cloudflare (налаштування); бот і фронтенд — адресу не задано. Для `not_configured` мережеві перевірки й опитування сторінок статусу провайдера не виконуються взагалі.
  - Майбутні сервіси (моніторинг доступності, пошта тощо) додаються в реєстр перевірок одним записом; реєстр — єдиний список у коді, документація генерується/звіряється з ним тестом.
- **Статус провайдера** (поле `provider` у записі стороннього сервісу): `{ "status": "operational | degraded | partial_outage | major_outage | maintenance | unknown", "url": "<сторінка статусу>", "checkedAt": "<ISO>" }` — з офіційних сторінок статусу у форматі Statuspage (`/api/v2/status.json`) чи аналогу, де вони є (Discord, Cloudflare, Backblaze, Axiom, Google Cloud — перевірити актуальні адреси під час реалізації); у Telegram офіційної сторінки немає — `provider` відсутній. Загальний `status` сервісу визначається нашою перевіркою; статус провайдера — пояснення («лежить у них»), і якщо наша перевірка `down`, а провайдер повідомляє збій — `message` про це каже. Опитування сторінок статусу — не частіше разу на 5 хв.
- **Формат відповіді** (стабільний контракт, `schemaVersion: 1`, описаний у `@nri/shared` zod-схемою й у `docs/ops/health.md`):
  ```json
  {
    "schemaVersion": 1,
    "status": "ok | degraded | down",
    "env": "local | dev | prod",
    "version": "<версія збірки>",
    "checkedAt": "<ISO>",
    "services": [
      { "id": "mysql", "kind": "internal", "required": true, "status": "ok",
        "latencyMs": 3, "checkedAt": "<ISO>", "message": null }
    ]
  }
  ```
  Загальний `status`: `down`, якщо будь-який `required` сервіс (`mysql`, `redis`, `worker`) не `ok`; `degraded`, якщо будь-який інший підключений сервіс `down | stale | degraded`; інакше `ok`. `not_configured` не погіршує загальний статус. `message` — коротка причина англійською, без секретів, адрес і токенів.
- **Ендпоінти:**
  - `GET /api/health/live` — без змін;
  - `GET /api/health` — без змін у полях (сумісність із документацією й моніторингом), HTTP 200/503 за обов'язковими сервісами;
  - `GET /api/health/services` — повний список у форматі вище. **Захищений токеном** `HEALTH_TOKEN` (заголовок `Authorization: Bearer …`): без токена — 401, якщо токен не задано в env — ендпоінт вимкнено (404). Рішення виконавця: публічний перелік підключених сервісів і їхніх збоїв — це розвідка для атакувальника; боти й моніторинг легко передають токен. Код відповіді 200 завжди, коли запит авторизований (стан — у тілі), щоб автоматизація не плутала «сервіс лежить» із «ендпоінт недоступний».
- **WebSocket-канал змін стану** (доповнення власника 2026-11-28 — не лише API):
  - Окремий простір імен Socket.IO `/health` на наявному сервері (`backend/src/realtime/socket.ts`, Redis-адаптер уже є — працює й з кількома інстансами бекенду). Авторизація при підключенні тим самим `HEALTH_TOKEN` (`auth: { token }` у handshake); без токена чи з хибним — відмова; токен не задано — простір імен не монтується. Сесійні cookie сайту тут не потрібні й не приймаються як заміна токена.
  - Одразу після підключення — подія `health.snapshot` з повним станом (той самий формат, що `GET /api/health/services`).
  - Далі — подія `health.changed` лише коли стан відрізняється від попереднього: `{ schemaVersion, status, previousStatus, checkedAt, changes: [{ id, kind, from, to, message }] }` (лише сервіси, що змінилися, і загальний статус). Без змін — тиша.
  - Коли перевіряється: періодично (опитувач, раз на 60 с) і за тригерами — збій внутрішньої перевірки під час звичайного `GET /api/health`, помилка звернення до стороннього сервісу в роботі застосунку (напр. відмова Telegram API при надсиланні), успішний/невдалий бекап, сигнал життя бота пропав. Тригер ставить позачергову перевірку відповідного сервісу (з придушенням дублікатів: не частіше разу на 10 с на сервіс).
  - Порівняння й розсилка — в одному місці (воркер), знімок попереднього стану в Redis, тож перезапуск не породжує хибних «змін» (після старту — `unknown` → фактичний, позначено як `startup: true`).
  - Підключених клієнтів не більше розумного ліміту (напр. 20 на інстанс), ping/pong і закриття неактивних — стандартні Socket.IO.
- **Перевірки сторонніх сервісів** не запускаються на кожен запит: фоновий опитувач у воркері раз на 60 с (кожна перевірка з таймаутом 3 с, поріг `degraded` — 1.5 с), результат — у Redis; ендпоінт віддає знімок з `checkedAt`. Внутрішні — як зараз (кеш 2 с). Ліміти сторонніх API не перевищуються (не частіше 1 разу на хвилину на сервіс).
- Логи перевірок — через логер Плану 23; без секретів.
- Тести на кожен статус кожного сервісу (заглушки мережі), на загальний статус, на авторизацію; typecheck/lint зелені; шаблони env (`HEALTH_TOKEN`), документація.

## Review Focus

- Ендпоінт не розкриває секретів, внутрішніх адрес чи версій бібліотек.
- Повільний чи завислий сторонній сервіс не сповільнює `/api/health` і не валить docker healthcheck.
- WebSocket: без токена неможливо підписатися; `health.changed` не шле дублікатів і не «блимає» після перезапуску.
- Відсутність ключів сервісу дає `not_configured`, а не `down`.
