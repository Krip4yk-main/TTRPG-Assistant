# План 26 — розгортання в кластер Кейна: налаштування лише з .env, міграції, бекапи, гілки beta/main

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** образи, які збирає GitHub, однакові для будь-якого сервера свого середовища; усе, що відрізняється між серверами, вмикається й вимикається лише через `.env` на сервері (його вручну ведуть власник і Кейн). Міграції безпечні для автоматичного запуску на боці кластера, бекапи працюють «з коробки».

**Spec:** рішення власника й Кейна в чаті 2026-11-28:
- гілки: `beta` — дев (бета-кластер), `main` — прод; увесь код спершу йде в `beta`, потім у `main`;
- жодних змінних репозиторію GitHub для налаштувань — усе в `.env` на сервері;
- dev-вхід вмикається/вимикається нашим перемикачем у `.env`, а не сторонніми змінними;
- міграції запускає Кейн; від нас — правильна структура: старі не запускаються вдруге, нові нічого не ламають;
- бекапи лежать на сервері й у Cloudflare R2; керуємо ними ми, у кластері вони просто працюють без додаткових налаштувань.

## Стан зараз

- `.github/workflows/deploy-dev.yml` (з чернетки Кейна): на пуш у `beta` збирає `ttrpg-backend`, `ttrpg-bot`, `ttrpg-frontend` у ghcr.io і пише дайджести в `deploy/images.yaml` гілки `deploy`. Фронтенд отримує налаштування як build-аргументи `NG_APP_*` з змінних репозиторію (`DEV_TELEGRAM_BOT_USERNAME`, `DEV_GOOGLE_LOGIN`, `DEV_DISCORD_LOGIN`, `DEV_TESTER_LOGIN`) — від цього відмовляємось.
- Фронтенд читає `telegramBotUsername`, `googleLogin`, `discordLogin`, `devLogin`, `deployEnv` з `runtime-config.ts`, згенерованого під час збірки (`frontend/scripts/gen-runtime-config.mjs`).
- Бекапи — окремий сервіс `backup` (`scripts/ops/Dockerfile.backup`): щодоби локально + rclone у R2/B2; у кластер цей образ не збирається.

## Global Constraints

- **Фронтенд без серверних налаштувань у збірці.** Ім'я Telegram-бота, увімкненість входу через Google/Discord фронтенд бере під час запуску з бекенду (новий публічний `GET /api/public-config` — лише те, що й так видно на сторінці: `telegramBotUsername`, `providers: { telegram, google, discord }`; кеш на хвилину). Бекенд виводить їх зі свого `.env` (`TELEGRAM_BOT_USERNAME`; `GOOGLE_CLIENT_ID`+`SECRET` задані → google увімкнено; так само Discord). Жодних прапорців dev-входу, версій, внутрішніх адрес у відповіді.
- **Що лишається у збірці — лише за гілкою, без змінних:** `beta` → `NG_APP_DEPLOY_ENV=dev` і прихований маршрут `/login/dev` у бандлі; `main` → `NG_APP_DEPLOY_ENV=prod`, коду dev-входу в бандлі немає (як у Плані 19). Робить це сам воркфлоу за назвою гілки.
- **Dev-вхід вмикається лише `.env` бекенду** (`DEV_LOGIN_ENABLED`, `DEV_LOGIN_CODES` — План 19). Сторінка `/login/dev` на беті, коли бекенд dev-вхід вимкнув (маршрут повертає 404), показує «Вхід для тестерів зараз вимкнено» замість форми.
- **Воркфлоу:** один файл `.github/workflows/deploy.yml` для обох гілок; без `vars.*`; образ `ttrpg-backup` збирається разом з трьома іншими; дайджести бети — як зараз (`deploy/images.yaml` у гілці `deploy`), прода — `deploy/images-prod.yaml` (див. «Домовленості з кластером»); теги `beta-<sha>` / `prod-<sha>`.
- **Міграції (запускає Кейн):** структура drizzle вже не запускає застосовані вдруге (журнал `__drizzle_migrations`) — задокументувати й закріпити тестом. Правила для нових міграцій у `docs/ops/migrations.md`: лише додавання/розширення (expand) у тому самому релізі, що й код, видалення/перейменування (contract) — наступним релізом, коли старий код уже не працює; без деструктивних змін без бекапу; міграція ідемпотентна щодо повторного запуску після часткового збою, де MySQL це дозволяє. Перевірка в тестах: (а) усі міграції застосовуються на порожній БД; (б) повторний запуск нічого не робить; (в) застосовані міграції не змінювались (контрольні суми SQL-файлів з журналу збігаються з файлами — змінений старий файл = помилка). Команда запуску міграцій для кластера — одна, задокументована (той самий образ бекенду).
- **Бекапи в кластері:** образ `ttrpg-backup` налаштовується лише через `.env` (ті самі `BACKUP_*` і rclone-змінні, що в `docs/ops/backups.md`): розклад, локальна тека (том на сервері) і копія в Cloudflare R2 — без ручних кроків у кластері, крім тому й `.env`. Перевірити, що образ працює з довільним UID (Kubernetes) і з томом, змонтованим ззовні.
- **Документ для Кейна** `docs/ops/cluster.md`: образи й що кожен робить, змінні `.env` для кожного сервісу (посилання на шаблони), порти, проби (`/api/health/live` — liveness, `/api/health` — readiness), WebSocket `/socket.io`, закрити `/api/internal/`, `TRUST_PROXY`, Redis з паролем, міграції (команда й порядок), бекапи (том, R2), прев'ю-боти й `sitemap/robots` (з README), гілки `beta`/`main`.
- Документація оновлена під гілки `beta`/`main` (`deploy.md`, `environments.md`, README, шаблони `.env` — прибрати згадки змінних репозиторію й `NG_APP_*` як налаштувань сервера).
- Тести/typecheck/lint/build зелені; секрети не друкувати; коміти з `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Домовленості з кластером (вирішено нами 2026-11-28; Кейн підлаштовує свій бік або просить змін)

Власник доручив визначити структуру самим і описати її в документі для Кейна (`docs/ops/cluster.md`).

1. **Образи:** ті самі імена для обох середовищ — `ghcr.io/krip4yk-main/ttrpg-{backend,bot,frontend,backup}`; теги розрізняють середовище, щоб збірки `beta` і `main` з одного коміту не перезаписували одна одну (фронтенд у них різний): `beta-<sha>` і `prod-<sha>`. Кластер бере образи **лише за дайджестом** із файлу дайджестів, теги — для людей.
2. **Файли дайджестів:** гілка `deploy` (лише файли дайджестів, робот пише туди, у `beta`/`main` не потрапляє): бета — `deploy/images.yaml` (як уже налаштовано в Кейна), прод — `deploy/images-prod.yaml`. Формат однаковий: рядок-коментар `# built from commit <sha>` і чотири ключі `backend:`, `bot:`, `frontend:`, `backup:` зі значенням `sha256:<64 hex>`. Новий ключ `backup:` — Кейн додає на своєму боці (новий сервіс-CronJob/Deployment).
3. **Продова частина воркфлоу** вмикається одразу (пуш у `main` пише `deploy/images-prod.yaml`); поки кластер прода не читає цей файл — просто нічого не відбувається.
4. **Міграції:** Кейн запускає окремий Job з образу `ttrpg-backend` тим самим дайджестом, що й бекенд, перед оновленням бекенду: `node --import tsx src/db/migrate.ts` (як сервіс `migrate` у `docker-compose.prod.yml`), з тим самим `.env`, що й бекенд. Повторний запуск безпечний (уже застосовані пропускаються). Бекенд стартує лише після успіху Job-а.
5. **Бекапи:** сервіс з образу `ttrpg-backup` працює постійно (власний планувальник усередині, як у compose), потребує тому для локальних копій і `.env` з `BACKUP_*`/R2; більше нічого.
