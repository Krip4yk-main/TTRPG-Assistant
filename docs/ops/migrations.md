# Міграції БД

## Як це працює

- Схема описана в `backend/src/db/schema/`, SQL-міграції лежать у `backend/src/db/migrations/`
  (`NNNN_назва.sql`) разом із журналом `meta/_journal.json`.
- Раннер — `backend/src/db/migrate.ts` (drizzle `migrate`). У таблиці `__drizzle_migrations`
  зберігаються хеш (SHA-256 файлу) і `created_at` (= `when` із журналу) застосованих міграцій.
  Застосовуються лише ті записи журналу, чий `when` більший за `created_at` останньої застосованої;
  решта пропускається. Тому повторний запуск безпечний і нічого не робить.
- Наслідок: `when` у журналі має строго зростати (перевіряє тест), а нова міграція ніколи не
  вставляється «посередині».

## Запуск у кластері

Одна команда, окремим Job-ом **перед** розкаткою бекенду (образ `ttrpg-backend`, той самий `.env`,
що й у бекенду, зокрема `DATABASE_URL`):

```
node --import tsx src/db/migrate.ts
```

Робоча тека — `backend/` в образі. Вихід `0` й рядок `migrations applied` — успіх. Якщо Job впав,
бекенд не розкочується.

Локально: `npm run db:migrate -w backend`.

## Правила нових міграцій

1. **Expand — разом із кодом.** Додавання таблиць/колонок/індексів (з дефолтом або nullable) іде
   в тому самому релізі, що й код, який їх використовує. Старий код має працювати з новою схемою,
   бо під час розкатки обидві версії живуть одночасно.
2. **Contract — лише пізніше.** Видалення й перейменування (`DROP`, `RENAME`, звуження типів,
   `NOT NULL` без дефолту) — окремою міграцією в наступному релізі, коли старого коду вже ніде немає.
3. **Застосовану міграцію не редагувати.** Помилку виправляє нова міграція. Зміна чи видалення
   наявного файлу валить тест `test/db/migrations.test.ts` (суми в `checksums.json`).
4. **DDL у MySQL не транзакційний.** Збій посередині міграції лишає частину змін застосованою,
   а запис у `__drizzle_migrations` не з'являється. Тому:
   - перед ризикованою міграцією (зміна даних, перебудова великих таблиць) зробіть бекап;
   - пишіть міграції так, щоб їх можна було безпечно повторити після часткового збою, де це
     можливо (`IF NOT EXISTS` / `IF EXISTS`, одна дія на файл, `INSERT ... ON DUPLICATE KEY`
     або `INSERT IGNORE` для даних);
   - після збою перевірте стан схеми й або повторіть Job, або вручну доведіть схему до очікуваної.

## Як додати міграцію

1. Змініть схему в `backend/src/db/schema/`.
2. `npm run db:generate -w backend` — drizzle-kit створить `NNNN_*.sql`, оновить журнал і знімок
   у `meta/`. За потреби перейменуйте файл і тег у журналі до першого застосування (або
   використайте `drizzle-kit generate --custom`, якщо потрібен ручний SQL).
3. Перегляньте SQL на відповідність правилам вище.
4. `npm run db:checksums -w backend` — допише суму нового файлу до
   `backend/src/db/migrations/checksums.json` (наявні суми скрипт не переписує).
5. `npm test -w backend` — тест перевірить, що міграції застосовуються на порожній БД, повторний
   запуск нічого не змінює, а зафіксовані файли не змінені.
6. Закомітьте SQL, журнал, знімок і `checksums.json` разом.
